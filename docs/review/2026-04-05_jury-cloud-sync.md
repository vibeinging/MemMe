## 各陪审员详细评审

### 系统架构师

**裁决**: ⚠️ 有条件赞成

**核心观点**: 需求方向正确——记忆数据需要跨设备持久化和灾备。但"云同步"掩盖了巨大的复杂度光谱。必须先明确同步模型再谈实现。

**详细分析**:

1. **现有基础设施比看起来的更"半成品"** — sync_version 只覆盖 memories 表，其他 15+ 张表没有变更追踪。要么只同步 memories（丢失知识图谱），要么其他表全量导出。

2. **DuckDB 单文件天然适合快照备份** — CHECKPOINT 可产出一致快照，replica.rs 已验证。行级增量合并会遇到严重障碍：无 WAL 流式复制、无 CRDT、embedding + HNSW 索引无法行级合并。选错路径会把 1-2 周项目变成 2-3 月工程。

3. **iCloud 对数据库文件不友好** — 大文件上传非原子性，多设备写入产生冲突副本，CloudKit 单条 1MB 限制，Android 不可用。

4. **"版本"需要精确定义** — 快照版本（Time Machine 式）vs 增量版本 vs 设备版本，方案差异巨大。

5. **数据大小与带宽约束** — 10K 条 memory 的 DuckDB = 50-200 MB，需要 WiFi-only + zstd 压缩。

**关键风险**:
- [高] 多设备冲突导致数据丢失
- [高] 隐私数据泄露（快照含 local_only 记录）
- [中] Schema 版本不兼容

---

### 安全工程师

**裁决**: ⚠️ 有条件赞成

**核心观点**: 现有代码有良好的隐私分级基础，但两个高危问题必须在同步功能上线前解决。

**详细分析**:

1. **数据明文上云** — 没有实际加密实现。必须在 Rust 层加文件级加密（AES-256-GCM 或 XChaCha20-Poly1305）。

2. **隐私标记绕过** — local_only 只保护 memories 表，events、episodes 等关联表没有隐私控制，原始对话内容仍会被同步。

**关键风险**:
- [高] 数据明文上云
- [高] 隐私标记绕过

**必须先回答**: 加密密钥由谁管理？

---

### 移动端工程师

**裁决**: ⚠️ 有条件赞成

**核心观点**: 备份利用现有 replica.rs + 云上传可 2-3 周完成；多设备同步至少 2-3 个月。

**详细分析**:

1. **并发写入风险** — 上传期间如果 meditation/compact 触发写入，可能导致上传文件不一致。建议上传 .replica 文件而非 primary。

2. **架构建议** — 定义 `CloudBackend` trait（类似 Embedder/LlmProvider），新建 `memme-sync` crate，Phase 1 只做 S3 兼容后端的整文件备份。

**关键风险**:
- [高] 并发写入导致不一致
- [中] 蜂窝网络下大文件传输

---

### 数据工程师

**裁决**: ⚠️ 有条件赞成

**核心观点**: 现有基础设施是为单设备本地备份设计的，直接用于多设备云同步会在冲突解决和数据完整性上产生严重问题。

**详细分析**:

1. **sync_version 不支持多设备并发** — 全局 MAX+1 递增在多设备下版本号冲突。
2. **sync_version 仅覆盖 memories 表** — 其他表只能全量。
3. **ON CONFLICT DO NOTHING 会丢更新** — import 无法合并，只能添加不能更新。
4. **replica 机制可直接用于云备份** — CHECKPOINT + 上传 .replica，开发量最小。
5. **schema 版本在导出中缺失** — 跨版本恢复可能失败。

**关键风险**:
- [高] 冲突丢失
- [中] 大文件上传效率
- [低] iCloud 文件冲突

---

### 产品经理

**裁决**: ⚠️ 有条件赞成

**核心观点**: 云同步是刚需，但必须严格分阶段，先做云备份+恢复，不要一上来就做多设备实时同步。

**详细分析**:

1. **备份/同步/版本管理是三件事** — 严格分阶段：P0 云备份与恢复（4-6周）→ P1 版本快照（2-3周）→ P2 多设备同步（另行立项）
2. **不要自建云** — 用平台原生能力，core 只提供加密导出接口
3. **加密是非谈判项** — AES-256-GCM + Argon2，用户自持密钥
4. **版本管理要克制** — 保留最近 5-10 个快照，FIFO 淘汰
5. **复用现有 replica/export 能力** — 新增加密层包装

**关键风险**:
- [高] 范围蔓延
- [高] 密钥丢失导致数据不可恢复
- [中] 跨平台云存储 API 碎片化

---

### 魔鬼代言人

**裁决**: ❌ 反对

**核心观点**: MemMe 是库不是应用。添加云同步是过早抽象，会增加维护负担、模糊产品边界、削弱 edge-first 价值主张。

**详细分析**:

1. **用户真的需要云同步吗？** — 现有 full_export/import + replica 已经给宿主应用提供了完整同步原语。
2. **iCloud/云盘对数据库文件是灾难** — 会导致 WAL 写入冲突、文件损坏、静默数据丢失。
3. **版本管理混淆了三件事** — 备份（已有）、审计日志（已有）、时间旅行（大量工作）。
4. **网络 I/O 引入零网络库** — 从根本上改变库的嵌入特性。
5. **Edge-first + 云同步是身份危机** — 与竞争对手在其优势领域竞争。

**替代建议**: 暴露 `checkpoint_to_path(path)` + 文档化 Sync Integration Guide，让宿主应用决定如何上传。

## 裁决总结

5:1 有条件通过。核心共识：P0 只做单向加密备份，Core 保持零网络依赖，只提供 checkpoint+加密+导出 能力，上传逻辑由宿主应用通过 FFI 完成。端到端加密是前置条件而非后续优化。不要把 DuckDB 文件直接放 iCloud Drive。

推荐架构：`CHECKPOINT → strip local_only → 加密(AES-256-GCM) → 输出到指定路径` 由 core 完成，宿主应用负责上传和版本管理。
